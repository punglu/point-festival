## 3. Naming principles adopted (source-derived, not invented)

- **PK**: `id` (integer `SERIAL`/`Integer`, except Doran's own tables which use `UUID` — see Table Dictionary `KEEP`/`UNKNOWN` split). Confirmed universal across all 33 tables introspected.
- **FK**: `<referenced_entity_singular>_id`, e.g. `player_id`, `family_group_id`, `service_principal_id` — with one confirmed inconsistency: `family_id` (path params, some function signatures) vs `family_group_id` (DB column, most response fields) refer to the identical value. See §4.
- **Boolean**: `is_*` (`is_locked`, `is_admin`, `is_active`, `is_dashboard_visible`, `is_system`, `is_read`) — consistently followed, zero `has_*`/`can_*` instances found.
- **Timestamp**: `*_at` (`created_at`, `updated_at`, `deleted_at`, `joined_at`, `left_at`, `revoked_at`, `closed_at`, `assigned_at`, `reviewed_at`, `published_at`, `next_attempt_at`, `locked_until` — the last one is the one exception, see §4) — consistently followed.
- **Date** (not time): `date` (bare column name, not `*_date`) is the actual convention on `missions.date`, `daily_points.date`, `cheer_messages.date`, `feedbacks.date`, `login_logs.date`, `deductions.date` — six for six. The candidate rule's suggested `*_date` suffix (§6.3 of the task prompt) is **not what this codebase actually does**; recording the observed convention rather than silently adopting the candidate.
- **Status**: `status` (String, not enum type) is the near-universal convention (`accounts`, `family_groups`, `family_memberships`, `roles` has no `status` but has `is_active`/`is_system` instead, `service_subscriptions`, `doran_rooms`, `doran_participants`, `service_principals`, `doran_service_bindings`, `service_outbox_events`, `missions`). All are `CheckConstraint`-enforced string enums, never a native Postgres `ENUM` type or a separate lookup table.
- **Type/Kind**: inconsistent — `room_type` (Doran), `message_type` (Doran), `event_type` (audit log, outbox), `mapping_status` (not `mapping_type`), `relationship` (not `relationship_type`), `scope_type` (Role). No single `type`-vs-`kind` convention; each domain picked its own qualified name (`<noun>_type`), never bare `type` or `kind` as a column name. The frontend independently uses `kind` for its own preview-only Doran room objects (`DoranPreviewRoom.kind`, `frontend/src/platform/doran/preview/types.ts`) — a naming choice that does not match any backend column name at all, since that object is fixture-only and never deserializes a real API response (see Gap Report).
- **Soft delete**: `deleted_at`, nullable timestamp — applied via `SoftDeleteMixin` (`backend/app/models/base.py`) to most tables, but explicitly and intentionally **not** applied to: `app_configs`, `login_logs`, `level_tiers`, `permissions`, `role_permissions`, `membership_role_assignments`, `roles` (has no soft-delete; has `is_active` instead), `service_principals` (has no soft-delete; has `revoked_at`+`status='revoked'` instead), `doran_participants`/`doran_messages`/most Doran junction tables (Doran has its own `status`/`deleted_at`(only `DoranRoom`,`DoranMessage`)-based lifecycle, not a blanket Mixin). This is a deliberate, per-table decision each domain made, not an oversight — see Table Dictionary's `soft_delete` column for the exact table-by-table split.
- **created_at/updated_at**: `TimestampMixin` (`backend/app/models/base.py`) is the standard pairing, but three legacy tables deliberately omit `updated_at` (`notifications`, `login_logs`, `feedback_replies` — each has an explicit code comment stating this matches `init.sql`, e.g. `backend/app/domains/notification/models.py:5`).

## 4. Synonym / naming-conflict findings (evidence-based, not invented)

1. **`family_id` vs `family_group_id`** for the identical value. DB column and internal model attribute is always `family_group_id` (`family_groups.id`, `family_memberships.family_group_id`, etc. — confirmed in every migration and model). But URL path parameters and several Python parameter names use `family_id` instead (`doran/router.py` prefix `"/api/families/{family_id}/doran"`, `family/service.py` function signatures like `get_active_membership(db, account_id: int, family_id: int)`). Response body fields are split: `AccountContextResponse`/`FamilySummary` don't repeat the id at all under either name at the top level; `MembershipSummary.family_group_id` uses the long form; `SubscriptionResponse.family_group_id` uses the long form. **Recommendation for a future contract, not applied here**: standardize on `family_id` everywhere (shorter, matches URL convention) or `family_group_id` everywhere (matches the DB); do not silently keep both.
2. **`total_points` vs `total_earned`** — see Business Glossary row above; two genuinely different numbers (spendable current balance vs. lifetime leveling input) with names similar enough to invite confusion. This is not a pure naming defect (the underlying concepts are legitimately different) but the names alone do not make that difference obvious to a new reader.
3. **`membership_id` vs `family_membership_id`** for the identical referenced entity (`family_memberships.id`) depending on which domain's schema you're reading: `family/schema.py`'s `MembershipSummary`/`RoleAssignmentResponse` say `membership_id`; `doran/schemas.py`'s `ParticipantCreate`/`ParticipantResponse` say `family_membership_id` (matching the DB column name exactly, which `family/schema.py`'s own version does not).
4. **Two independent get_current_user functions, same name, different behavior**: `app/dependencies.py::get_current_user` (HTTPBearer, accepts `role in {player, admin}`, returns the full raw JWT payload dict with `sub`/`role`/etc.) vs `app/domains/auth/dependencies.py::get_current_user` (OAuth2PasswordBearer, accepts **only** `role == player`, returns a normalized `{"player_id": int, "is_admin": bool}` dict). Both are actively imported by different routers (`family`/`cheer`/`config`/`daily_point`/`level_tier`/`notification`/`mission`/`deduction`/`login_log`/`player`/`doran` use the `app.dependencies` version; `chat`/`admin`/`mission_template` use the `auth.dependencies` module for their own admin/chat-specific variants, though none of them actually import the auth.dependencies *`get_current_user`* itself — they use `get_current_admin`/`get_current_chat_user` from that same module instead). Not a bug (Python's own scoping means there is no runtime collision — every import site resolves to exactly the function it names), but a significant readability/maintenance hazard: grepping for "get_current_user" without also checking the import line silently picks the wrong one.
5. **`kind` (frontend Doran preview fixture) vs `room_type` (real DB/API)** — see the Type/Kind principle note above. Not a live contract mismatch today only because the frontend Doran UI does not call the real API at all yet (see Gap Report); it would become a real, immediate contract mismatch the moment that wiring is attempted, since the field name itself differs (`kind` vs `room_type`), not just its values.
