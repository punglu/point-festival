## 3. Execution tool selected for this task

**`pnpm` — invoked as `pnpm --dir frontend run <script>` (or `cd frontend && pnpm run <script>`).**

1. **Evidence for this judgment**: §1 above — node_modules is pnpm-shaped (`.pnpm/` present, no npm install marker), and a live `pnpm dev` process is already successfully running against this exact tree.
2. **Runs without install**: `pnpm run lint` and `pnpm run build` were executed this session (see Baseline Gate, §12 companion) using only the pre-existing `node_modules` — no `pnpm install`, `npm install`, or `npm ci` was run at any point.
3. **Does not change any lockfile**: `pnpm run <script>` (as opposed to `pnpm install`) does not resolve or write `pnpm-lock.yaml`. Confirmed post-hoc: `sha256sum frontend/pnpm-lock.yaml` before and after running lint+build is identical (`1c10764b8b4713e5ad873d8acce1f1c6eae99645d8d8696bc451392cd527c985`), and `git status` still shows `package-lock.json` as `D` and `pnpm-lock.yaml` as `??` — unchanged state, not newly modified.
4. **No conflict with existing dirty**: neither lockfile was written to, read-modified, staged, or deleted by this task. Both remain exactly as classified `PRE_EXISTING_PRESERVED_DIRTY` in the Start Gate.
